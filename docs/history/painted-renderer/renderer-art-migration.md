## Scope and architecture

Replace the presentation inside the existing Three.js renderer, retaining the MapView contract, simulation, actual HUD and save format. Start behind an opt-in development look switch with the existing look available for comparison. Extract reusable assets and surface code rather than importing the mockup's monolithic scene.

Relevant seams: `src/render3d/layout.ts` currently provides a single tileTopY per tile; `picking.ts` uses height classes; `board3d.ts` owns terrain and asset registries; `roads3d.ts`, `improvements3d.ts`, `cities3d.ts`, `pieces.ts` and `overlays.ts` consume placement information. Renderer projection, fog, wrap copies and animation also need to agree with new surface geometry.

Define a deterministic tile-local surface API returning height and normal, plus placement footprints and connection anchors. Mesh generation and sampling must use the same triangulation (or identical interpolated surface), not approximately matching formulas. Preserve wrap-aware coordinates and stable per-tile variation. Picking should hit the visible surface, including raised edges, with tile candidates/spatial filtering rather than scanning a whole world's triangles.

Ground markings use subdivided surface-following ribbons with shared joins and small depth bias. Roads need deliberate ramps across tile height changes, matching junctions and city gates; a floating ribbon is not a solution. Rigid buildings stay upright on locally flattened pads or fitted foundations; fence segments and fields conform separately. Reserve footprints and road corridors before scattering vegetation. Water assets use the water datum. Depth-tested territorial ribbons stay occluded by scene objects.

## Review sequence

1. **Surface and placement proof — visually approved.** A fixed fixture using real tile data and the new shared modules: flat land, hills, mountain, coast; road straight/turn/junction, flat-to-hill ramp, city entry, farm, hill mine and territorial border under scenery. Reviewed at game zoom and close-up. Focused topology and terrain-fit checks pass. Picking, wrapping and live-state correctness remain to be verified in the playable stage.
2. **Playable terrain slice.** Opt-in look in the actual game, real HUD, movement, fog/reveal, rivers, lakes, shores, world wrap and selection/reachability/path overlays. Cover all nine terrain types and forest/jungle/oasis/floodplain. Existing assets may remain temporarily. Exit: readability under real interaction and actual camera; record an early standard-board performance baseline before asset expansion.
3. **City kit.** Review all three owner-age sculpt tiers and population-driven house counts, with/without walls, capital/shrine/temple/wonder indicators, religion and puppet state. Current walls correspond to the palisade building, with its existing age-based appearance changes; do not invent a new gameplay upgrade. Include occupied city, gate-to-road connection, hill/coastal placements and city banner clearance. First approve one city plus walls, then remaining variants within this stage.
4. **Improvement catalogue.** Three sub-reviews: farm/mine/pasture/camp/quarry; plantation/lumbermill/fishing boats; academy/landmark/manufactory/customs house/citadel/holy site. Present each on valid representative terrain beside a unit and road; include resource coexistence, clutter-clearing rules and any existing pillage/state visuals. Asset list follows the current game scope. Floating gardens are excluded at the user’s direction (September 12).
5. **Unit-line kits.** User direction: keep one shared base model per existing unit line (infantry, anti-cavalry, cavalry, etc.), with individual types remaining mostly the same. Audit the current sculpt/line mapping before authoring; broad data modelClass values alone are not the line specification. First review representative line bases at normal game zoom, then a side-by-side progression within one line. Different lines need clear silhouettes; variants within a line need only a small number of changes, such as weapon/headgear, shield or armour details. Reuse bodies, poses, bases and materials. Avoid colour-only differentiation because colour must still communicate ownership and selection. Expand to the remaining lines in small review batches using the approved approach. Cover all 61 data IDs through an explicit line-to-variant mapping, not 61 separately authored models; inventory runtime variants such as embarked appearances and great-person families as well. Review owner colours, enemy/selected states, stacked pieces, damage, movement and garrison clearance.
6. **Combined gameplay review.** Fixed seeded maps and curated situations with the entire new look: crowded improved cities, border forests, narrow coast, mixed elevations and battles. Check labels, yield/resource markers, lenses, fog, animation and actual UI together. User plays/inspects and approves composition before final tuning.
7. **Performance and default rollout.** Measure load/build time, frame-time distributions while panning/zooming and moving, draw calls, triangles and memory on the real standard map and a larger stress map. Record browser/device/DPR and warm-up. Target 60fps on the agreed reference machine, with scalable shadows/foliage for weaker devices; do not promise this before measuring. Batch terrain in chunks, instance shared assets, cache static work, and retain detail where silhouettes need it. Run relevant renderer/UI tests and build/type checks; make the look default only after the final visual review.

## What each review contains

A named preview/fixture with a resettable camera, normal game-zoom view and detail view; a short list of changed elements and remaining limitations; relevant checks and performance notes. Approved assets remain visible beside new ones for comparison. Stop for the user's eye check at each numbered gate and each catalogue sub-review. Keep production UI changes separate from renderer tuning unless a concrete collision requires a proposed adjustment.

## Assets and scope risks

Asset authoring can begin with custom mesh builders and shared materials already available. Use authored GLB meshes for shapes that are awkward to express convincingly in code; Blender access is optional until that need is demonstrated. Automated generation alone is not a guarantee of reference-quality sculpting. Choose the workflow on the first representative pieces before multiplying it across the roster.

Beyond the explicit request, resource props, special sites, rivers, fog and gameplay overlays must retain readable coverage; replacing terrain while forgetting these would leave a visibly mixed renderer. Benchmark throughout, not just at the end. The mockup's small-scene performance does not establish production-map performance.
